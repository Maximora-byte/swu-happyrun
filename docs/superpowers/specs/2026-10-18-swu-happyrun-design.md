## 1. 目标与已确认需求

建立面向西南大学步道乐跑的统一仓库，同时推进 Windows/MuMu 执行端、服务器调度端，以及 vivo X200 Pro 无 Root 环境的兼容性研究。电脑端与服务器端必须共用任务、配置和结果模型。

用户已认可先完成 MuMu 的完整流程，再适配 vivo；服务器端同步开发。服务器首版通过在线 Windows 执行代理和 MuMu 完成任务。纯 HTTP 接口直传属于独立适配方向，当前尚无适用于西南大学当前客户端的可用性证据。

“完整支持”的验收对象是明确的步道乐跑版本、学校规则、设备和运行环境组合。只有客户端流程和服务端最终记录均通过检查，才可将该组合标为已验证；不能用单元测试通过代替实际记录有效，也不能承诺未来版本始终可用。

## 4. 方案选择

采用“服务器调度 + Windows 执行代理 + 可替换设备驱动”。相较于直接拼接两个参考仓库，这一结构能够把无 Root MuMu、未来 Android 驱动和后续接口适配放在相同任务契约下。

不选择 Root/LSPosed 作为首版前提，因为用户手机当前没有 Root。不选择纯接口作为首版唯一执行途径，因为尚未得到当前版本和学校配置的有效请求契约。

服务器端与执行端同步实现和联调。vivo 路径同步完成能力识别与兼容性记录，只有在该设备上通过端到端验收后才开放执行能力。不能以普通模拟位置能写入系统，推断步道乐跑会接受该位置。

## 5. 仓库与模块

使用 Python 3.11+，提供命令行工具和可容器化的服务器。核心逻辑与设备驱动分离，第一版不引入独立 Android APK 或完整网页管理系统。

- `core`：配置校验、坐标转换、路线解析、学校规则、任务状态机和结果模型。
- `drivers`：MuMuManager、MuMu 本机通道、ADB 和步道乐跑界面适配；每项能力必须先探测再使用。
- `agent`：连接设备、领取任务、续租、运行与恢复、采集经脱敏的验证结果。
- `server`：认证、任务持久化、调度、执行租约、状态与结果查询；初版使用 SQLite。
- `cli`：环境自检、配置管理、路线检查、任务执行、代理启动、服务器启动和结果查询。
- `profiles`：学校与客户端适配格式及说明；不提供编造的西大校区边界、打卡点或学期指标。
- `tests`：有实际行为断言的单元、协议和集成测试，以及可重放的界面样本。
- `docs`：安装、首次接入、客户端版本矩阵、服务器部署、故障恢复和验收证据。

## 6. 统一任务与状态机

任务包含唯一 ID、学校配置版本、路线版本、设备选择、目标条件、允许时间窗口和执行选项。服务器使用 Asia/Shanghai 解释用户日程，内部保存 UTC 时间。

正常状态为 `queued -> leased -> preflight -> ready -> running -> finishing -> verifying`。设备任务经过真实记录核验才进入 `succeeded`；模拟任务进入 `completed`。异常终态为 `failed`、`cancelled`；`needs_attention` 为保存恢复阶段的非终态，`cancelling` 等待设备停止确认。任何状态迁移均记录时间、原因和执行代理。

- 一台设备同一时刻只允许一个任务；代理本地设备锁与服务器租约同时约束。
- 开始前必须核对已登录账号的学校配置、有效时间、位置通道和必要权限。
- 动态打卡点来自当前会话的实际信息。没有可信坐标或路径时转为 `needs_attention`，不编造坐标后继续。
- 退出信号、取消和错误必须停止定位与传感器任务，释放资源并记录结果。
- 上传超时不能直接判为失败后再次创建跑步记录；先核查已有记录，再决定重试或请求人工处理。
- 代理断线后服务器不直接把已开始任务重新派发给其他设备，避免重复执行。
- `succeeded` 要求存在可核验的最终记录和有效状态；只有本地轨迹执行完成时保留为尚未核验。
- 租约使用单调递增 fence，任务更新使用 revision，事件以 event_id 幂等处理。开始操作须先记录服务器意图并写入代理本地日志；结果不明确时禁止自动重启任务。
- 地图上的动态打卡点不保证能从界面树获得。第一版允许用户确认真实点位；自动识别必须单独验证数据来源、坐标映射与准确性，未知数据进入 `needs_attention`。

## 7. MuMu 与步道乐跑适配

环境自检先发现 MuMu 路径、宿主版本、实例索引、Android 引擎与运行状态，再定位对应 ADB 通道和目标应用版本。所有命令通过参数列表执行，设置超时并检查返回码和结构化错误。

坐标输入必须明确标注 WGS-84、GCJ-02 或 BD-09。内部统一使用 WGS-84。MuMu 输入坐标系通过驱动能力与实际探针确认，不能对 Android 12/15 不加区分地使用固定预补偿。

路线以用户提供的真实路点或可信道路数据为依据，先检查坐标范围、距离、连通性、闭环和学校允许区域。路线执行器按单调时钟推进，支持暂停、继续和停止，定位与传感器工作线程共享明确的取消状态。

步道乐跑界面适配使用 ADB 获取的界面树和明确的版本配置，必要时采用经校准的屏幕识别。未知页面、授权、验证码或其他需要本人操作的步骤进入 `needs_attention`。不能仅按固定屏幕坐标盲点开始和结束按钮。

完整流程覆盖：首次手动登录与配置采集、规则检查、开始、当前打卡点识别、路线执行、结束、上传状态和记录回查。网络异常、应用升级和界面变化必须产生可解释的错误或待处理状态。

## 8. 服务器与代理协议

服务器提供健康检查、任务创建/查询/取消、代理登记/心跳、任务领取/续租、状态事件与结果提交。API 路径统一放在 `/api/v1`。

代理主动连接服务器领取任务，避免服务器直连个人电脑 ADB 或 MuMu 控制端口。管理令牌与代理令牌分离；代理只能操作分配给自己的任务，首次登记不允许任意匿名客户端自动加入。

服务器初版按单一用户部署，SQLite 保存任务、日程、代理、租约与事件。任务创建支持幂等键，状态更新检查当前租约和状态版本。重启后可恢复日程，过期任务按配置跳过，避免补跑堆积。默认只监听回环地址；远程部署通过 HTTPS 反向代理接入。

实现使用 Python 3.11+、Pydantic v2、FastAPI/Uvicorn 与 SQLite。包名 `swu_happyrun`，命令 `swu-happyrun`。初版单进程、单调度器；HTTP 超时 5 秒、心跳 10 秒、租约 30 秒。AGENT token 绑定代理身份；ADMIN token 独立。依赖在实现时锁定并验证 Windows/Linux 安装。

本地账号会话保存在设备中，服务器不需要保存用户乐跑密码或社交登录凭证。日志默认不包含令牌、完整请求头、个人账号信息和连续位置记录；诊断导出由本地显式操作生成。

## 9. vivo 无 Root 路径

首先检测实际 Android 版本、ABI、ADB 授权和安装包兼容性，并记录普通位置模拟与虚拟机途径的可用性。`LocationSpoofer` 不满足当前无 Root 前提，不自动安装 Root、LSPosed 或改变系统安全设置。

手机路径与 MuMu 使用同样的学校配置和任务结果模型，但不能共享未经验证的设备能力标记。如果只有流程辅助可用，则明确报告该能力范围；如果目标应用拒绝运行环境，记录真实失败，不显示为“已完整支持”。

## 10. 纯接口方向

服务器模块从第一版起真实可运行，不能只留空接口。直接连接步道乐跑的协议执行器另行接入：先取得用户自身会话下的真实请求样本，再确认客户端版本、学校身份、签名、开始/结束契约与记录回查。

在上述证据齐全前，不发送根据猜测构造的跑步上传请求，也不把其他院校小程序参数作为西大正式支持。该方向研究不能阻塞服务器与 MuMu 代理的开发和联调。

## 11. 验证与验收

自动验证覆盖坐标基准与误差、路线距离和边界、时间窗口、状态迁移、取消、子进程超时、驱动响应、租约排他性、幂等提交、断线恢复、权限隔离和日志脱敏。

服务器与模拟执行代理的集成测试覆盖创建、领取、运行、续租、结束、查询、取消和重启恢复。这类测试只能证明调度协议，不证明步道乐跑接受运动记录。

MuMu 实测要求记录宿主版本、Android 引擎、步道乐跑版本、学校配置版本、探针定位/传感器数据，以及实际应用的完整流程结果。vivo 单独记录设备实测结果。最终有效状态可能需要延迟查询，未取得结果前保持“待核验”。

验收矩阵使用 `not_tested`、`host_verified`、`device_verified`、`record_verified` 四级，每项标记都绑定实际证据和日期。测试数据、虚拟学校和模拟服务不得取得后两级标记。

## 12. 交付范围与实施顺序

第一阶段先建立共享契约，并同时推进两个可独立验收的工作流：本地 Codex 负责 MuMu Android 15 能力探测、Windows 执行代理；云端 ChatGPT Dot 负责可运行服务器、调度与模拟代理联调。具体任务、文件边界和接口见开发计划。

第二阶段在真实步道乐跑环境中完成版本配置、学校规则与路线采集、运行过程和结果核验。需要本人登录或设备确认时保留明确的待处理状态。

第三阶段完成 vivo 无 Root 兼容性实测；纯接口执行器在得到真实协议证据后接入。仓库随交付列出各阶段真实完成状态和残余依赖。

交付包含可安装源码、命令示例、服务部署配置、运行说明、自动检查和兼容性证据。发布到 GitHub 时保留第三方归属与来源提交，不随仓库分发账号信息、现有 APK、视频或未获许可的正文。

## 13. 设计自查

- 两种使用入口共享一个执行与验收模型，服务器端有独立的真实交付范围。
- 当前设备事实与未来适配计划分开记录；未声称 vivo 或 MuMu Android 15 已通过乐跑实测。
- 未指定虚构的西大学校 ID、坐标、校区边界、配速、次数和学期规则。
- 上传成功提示、本地模拟完成与最终有效记录有不同的验收标准。
- 任务重试、租约过期、取消和未知界面均有明确定义，避免默默重复提交。
