# Issue 41 Task 4: recovery proof mapping and namespace tests

The plan's `hasPersistedCompletion(jobId, sessionId, fence, specDigest)` is implemented by `RemoteJournal.completedForRecovery(jobId, sessionId, fence, specDigest)`. Parameter order and meaning match. This is a local durable-journal predicate, not another wire protocol or a generic verification-reason success check. The implementation name is more restrictive: it requires an exact current binding, healthy replayed journal, unchanged job/session/spec, matching original start/finished-stop fences, and a strictly newer current authorization fence. `false` or an exception cannot authorize completion. The runner invokes it only for a simulation `verify_only` grant with current lease checks; recovery never creates the finished proof.

Origin/agent/device are selected outside this predicate by the Activity's SHA-256 journal-directory namespace. `RemoteNamespaceProofTest` reflects the actual production namespace method rather than reimplementing it. Each test writes and closes real finished proof, changes exactly one namespace input, opens a fresh journal with the same job/session/spec and fresh fence, and verifies no start or completion proof is visible. Reopening the original namespace still proves completion. The tests only use unique application cache subdirectories and synthetic identifiers; no networking or root commands.

Dependencies: frozen native recovery a83af3f1663da197a962bd34a3718a0ace238b4b150650ec2a2520478c265718 and foreground Activity with its existing private static namespace method. No production files are changed. These are instrumentation cases requiring Android execution; source inspection or JVM stubs are not ART acceptance.

Remaining Task 4 evidence is separate: actual Activity recreation/background behavior, kill/restart authorization, old-process lease-loss stopping, and changed-fence old-process rejection must be assessed against real HTTPS/Android scenarios. Namespace tests alone do not establish those properties.
