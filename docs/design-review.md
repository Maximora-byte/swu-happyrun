# 设计评估

日期：2026-10-18。评估对象：初版设计提交 `687d0be`。

## 结论

保留“云端调度 + Windows 执行代理 + 可替换驱动”。它符合用户已有 MuMu 和无 Root vivo 的条件，也允许服务器与设备端独立开发。初版文档足以说明方向，但缺少可执行的协议、故障恢复语义和实测前置条件；直接按其并行实现会产生接口分歧和重复操作风险。

以下修订已经写入设计及 v1 契约。这里的“已修订”指设计已修正，不代表功能已实现。

| 优先级 | 问题与影响 | 修订 |
| --- | --- | --- |
| P1 | 未验证 Android 15 就计划完整自动流程，可能在设备或应用入口即失败 | L0 独立能力探测；服务器用模拟代理同步开发。设备功能按真实探针逐项解锁 |
| P1 | 动态打卡点可能只存在于地图图层，界面树不一定包含坐标 | 明确来源和置信度；第一阶段支持用户确认的真实点位。自动识别单列可行性门槛，未知数据停在 `needs_attention` |
| P1 | `needs_attention` 被写为终态，与本人登录、确认后恢复冲突 | 定义为非终态，保存恢复阶段；已有运行副作用时只允许先核验或受控停止 |
| P1 | 租约、取消和上传超时缺少事务边界，可能重复开始或重复上传 | 原子领取、递增 fence、状态 revision、事件幂等、本地操作日志；取消等待设备确认；未知结果禁止重新开始 |
| P1 | 缺少双端接口与文件所有权，并行工作可能互相修改共享模型 | 固定 `/api/v1`、v1 消息、目录责任、独立分支与契约变更流程 |
| P2 | 验收等级没有明确来源，模拟服务可能被误当成有效记录 | 证据按组件/版本记录；simulation 只能 `completed`，设备任务仅在最终记录核验后 `succeeded` |
| P2 | SQLite 并发、日程漏执行、数据保留与服务器作用范围不明确 | 初版单进程单调度器；事务抢占；过期任务跳过；服务器不持有乐跑登录凭证；先交付部署文件 |

## 技术依据

- [MuMu 参考项目](https://github.com/EdmundMad0309/budao-lepao-runner/tree/53715ec80b3c5f0f99ef963e6cf5ed7be1a31e25) 明确面向 MuMu 12，并依赖人工先进入跑步界面。其控制代码可供研究，但不能证明 Android 15 全自动流程可用。
- [LocationSpoofer](https://github.com/HuangZhuoRui/LocationSpoofer/tree/43ebe9dc89082c4ebe45056c1806cc713effc589) 要求 Root/LSPosed，不能直接满足当前 vivo 条件。
- [SQLite 事务文档](https://www.sqlite.org/lang_transaction.html) 说明 `BEGIN IMMEDIATE` 提前开始写事务，并可能遇到其他写者导致的忙状态。因此领取与更新要短事务、有限等待、显式冲突响应。
- [FastAPI 测试文档](https://fastapi.tiangolo.com/tutorial/testing/) 支持使用 TestClient、HTTPX 与 pytest 测试服务器，无需连接真实设备。

## 发布与验收门槛

1. 契约、服务器和模拟代理通过，才能声称“调度流程可用”。
2. MuMu 的定位/传感器探针通过，只能声称相应设备能力可用。
3. 指定客户端版本在指定学校配置下出现并保留有效记录，才能标记该组合 `record_verified`。
4. vivo 和纯接口执行器分别验收。任何一项未通过都不阻塞已完成服务器模块的交付，也不被隐去。
